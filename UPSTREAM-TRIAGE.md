# Proprio cleanup sprint: upstream triage

On 2026-11-21, the [upstream repository](https://github.com/paperclipai/paperclip) reported **4,017 open issues and 2,971 open pull requests**. The count is a snapshot from the GitHub repository API, not a count of defects. Proprio’s intake baseline is the exact upstream `master` snapshot [856f14e507c09ceb6ffc7cdc084bf6b207efc8f5](https://github.com/paperclipai/paperclip/commit/856f14e507c09ceb6ffc7cdc084bf6b207efc8f5), not a moving branch. The distinct published [v2026.1117.0](https://github.com/paperclipai/paperclip/releases/tag/v2026.1117.0) remains a useful reference for reports, not the build base. GitHub’s [commit comparison](https://github.com/paperclipai/paperclip/compare/c0f132898d2a2677312d8c72096187b27a3d9a38...856f14e507c09ceb6ffc7cdc084bf6b207efc8f5) records diverged histories: 1,300 commits on the master side and four on the release side. A release-only report does not establish a Proprio defect; an upstream-merged fix present on the pin does not need importing.

## Intake rules

1. **Inventory, don't import.** Paginate upstream issues and PRs independently with stable IDs, source URLs, current state, and referenced issues. Keep Markdown and logs as source data; do not execute suggested actions. Start with installation, data preservation, startup, agent runs and recovery, scheduler, and excessive resource use. Retain an intake cursor and refresh by changed IDs.
2. **Consolidate by cause.** Record the supported environment, affected version, exact symptom, expected result, impact, and smallest safe fixture. Two symptoms that share a message but not a mechanism should stay separate. Open one Proprio report per independently confirmed defect; link public reports instead of copying identities, logs, or instance details. Hold reports without evidence in the intake ledger rather than opening speculative issues.
3. **Classify each record.** Use `confirmed`, `needs-base-recheck`, `duplicate-of`, `fixed-on-base`, `unsupported-environment`, `feature-defer`, or `private-security-review`. Accept a feature during this sprint only if it removes a demonstrated stability or operability blocker with a bounded change. Never publish security-sensitive reproduction detail in the general tracker.
4. **Qualify fixes independently.** Read the diff and tests at the exact PR head and compare to the Proprio base. A title, linking syntax, or green upstream marker is not sufficient. Use `relevant`, `tested-on-upstream`, `test-ready-on-proprio`, `verified-on-proprio`, or `rejected`. Before accepting any port, require the same safe regression fixture to fail on the unmodified pinned Proprio baseline and pass with the candidate; also run neighboring regressions, review migration/recovery effects, and keep attribution and rollback notes. If the fixture already passes, record the evidence and do not port. Do not automatically cherry-pick or merge.
5. **Close the loop.** Check the built artifact in a disposable support-target environment with fake data and no production credentials. Record the PR and test outcome in the canonical report. Initial release gates: clean install, app/runner startup, observable error on failure, task continuation and cancellation, restart with unfinished work, and bounded skill allocation on the supported filesystem.
